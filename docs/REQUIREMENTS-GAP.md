## ✅ (해소됨) 1. 원가·통계 열람이 실무자에게도 열려 있었다

**2026-08-20 수정.** `product_cost_summaries` 의 전체 개방 `read` 정책을 걷어내고
`admin read ... using (is_admin())` 로 바꿨다. 뷰 2개에는 `security_invoker = true` 를
걸었다 — 뷰는 기본이 소유자 권한이라, 이게 없으면 `v_cost_trend_monthly` 가
그 RLS 를 통째로 우회한다.

마이그레이션: `supabase/migrations/2026-08-20_admin-only-cost-read.sql`
**SQL Editor 에서 실행해야 반영된다.** 2026-08-20 실행 완료.

검증(브라우저 콘솔, `product_cost_summaries` · `v_cost_trend_monthly` 직접 조회):

| 계정 | 결과 |

| 실무자 `worker1234` | 둘 다 0 행 |

> "실무자는 데이터 입력만, 관리자는 분석 및 가중치 조정 가능" (01:03:11)

`product_cost_summaries` 를 포함한 **모든 테이블을 로그인한 누구나 읽을 수 있다.**

## ❌ 2. 실무자가 인건비 가중치를 조정할 수 있다

> 미팅: "인건비 등은 제품별 가중치(퍼센티지)로 조정 가능, 관리자에서 입력" (33:38, 39:53)
> "관리자는 분석 및 가중치 조정 가능" (01:03:13)

**현재:** `App.tsx` 의 worker 분기가 2단계를 포함한다.

```
if (loginRole === 'worker') {
  page = route === 'data-entry-2' ? <OperatingCostEntryPage/> : <RawMaterialEntryPage/>
}
```

2단계는 인건비 총액과 **제품별 배분 퍼센트**를 입력하는 화면이다.
RLS 상으로도 `operating_costs` 는 `editor draft write` — 실무자도 쓸 수 있다.

미팅대로라면 가중치 조정은 관리자 몫이다.
다만 "실무자는 원부재료·기타비용·생산량을 입력한다"(36:44, 42:05)와 겹치는 부분이 있어,
**2단계 중 어디까지가 실무자 몫인지 확인이 필요하다.**
(경비 금액 입력은 실무자, 가중치 조정은 관리자 — 로 나뉠 가능성)

## ❌ 3. 선입선출 평균 단가가 없다 — 가장 큰 구멍

> 미팅: "평균 단가는 선입선출법으로 계산, 이월 재고와 당월 매입 합산 후 평균" (22:16, 23:30, 49:10)
> "월별, 연말 평균 단가 산출" (47:23, 48:43)
> "월별 누적 평균 단가 제공" (53:20)

**현재:** 이 개념이 시스템 어디에도 없다.

| 필요한 것 | 현재 |
|---|---|
| 이월 재고 수량·금액 | 테이블 없음 |
| 당월 매입 수량·금액 | 테이블 없음 |
| 가중평균 단가 계산 | 없음 |
| 월별 누적 평균 | 없음 |

지금 단가는 두 군데서 온다:

- `materials.unit_price` — **현재 값 하나뿐.** 이력이 없다. 고치면 과거가 소급되지 않도록 스냅샷으로 막아뒀을 뿐, 평균 계산은 아니다.
- `material_usages.unit_price` — 그 달 수불자료에 적힌 단가를 **그대로** 쓴다.

즉 현재 원가는 "장부에 적힌 단가 × 소요량"이지, "선입선출 가중평균 단가 × 소요량"이 아니다.
미팅에서 반복해서 강조된 항목(22:16, 23:30, 47:23, 48:43, 49:10, 53:20)이라
**요구의 핵심일 가능성이 높다.**

구현하려면 최소한:

- 재고 이월 테이블 (월별 기말 수량·금액)
- 매입 입력 경로 (현재 수불자료는 *소요량*만 담고 매입은 없다)
- `confirm_period()` 가 평균단가를 계산해 쓰도록 변경

수불자료 엑셀에 매입 정보가 들어 있는지부터 확인해야 한다.
현재 파서는 `품명 | 수량 | 단가 | 금액` 네 열만 읽는다.

## ✅ (해소됨) 판매가 미입력이 "정상 0%"로 보이던 문제

`confirm_period()` 는 `sale_price = 0` 일 때 마진율 0, 상태 `normal` 을 저장한다.
DB 값은 그대로지만, 화면에서 **"판매가 미입력"** 으로 구분해 표시하도록 바꿨다
(대시보드 수익성 표 · 3단계 원가 표).

DB의 `status` 컬럼 자체는 여전히 `normal` 이므로, 쿼리로 직접 볼 때는 주의해야 한다.

## ✅ (해소됨) 판매가·포장무게 입력 경로가 없던 문제

## ⚠️ 8. `reviewer` 역할이 관리자 화면으로 들어간다

**2026-08-20 일부 수정.** 사용자 관리의 역할 드롭다운에서 `reviewer` 를 뺐다
(`ASSIGNABLE_ROLES`). 이미 그 역할인 사용자가 있으면 그 사람 칸에만 남는다.
enum 값과 `toLoginRole()` 매핑은 그대로다 — §1 수정 이후 reviewer 는
관리자 화면에 들어가되 원가가 0 행으로 보이므로, **쓸 거라면 열람 범위를 정해야 한다.**

### (기록) 원래 지적

> 미팅: "실무자 1명, 관리자 1명 정도만" (03:57)

**현재:** `user_role` enum에 `admin` `entry` **`reviewer`** 세 개가 있고,

```ts
toLoginRole = (role) => role === 'entry' ? 'worker' : 'admin'
```

`reviewer` 는 `admin` 화면으로 매핑된다. 즉 **원가·통계를 다 본다.**
쓰기는 RLS가 막지만 열람은 관리자와 동일하다.

미팅에서 요구하지 않은 역할이므로, 쓰지 않을 것이면 제거하거나
열람 범위를 정해야 한다. 사용자 관리 화면의 역할 드롭다운에 노출되고 있다.

## 미팅에 없는데 구현된 것 — 범위 확인 필요

**판매가·마진율·수익성 대시보드**

미팅 내용은 처음부터 끝까지 **원가 산출**에 관한 것이다.
판매가(`sale_price`), 마진율(`margin_rate`), 수익성 상태(`normal`/`watch`/`risk`)는
미팅 어디에도 언급이 없다.

현재 대시보드의 메인 표는 "수익성 현황"이고 마진율이 핵심 열이다.
`confirm_period()` 도 마진율을 계산해 저장한다.

이게 별도로 합의된 것인지, 아니면 초기 목업이 그대로 남은 것인지 확인이 필요하다.
**만약 합의되지 않은 기능이라면 문제가 있다:**

```sql
case when sale_price > 0 then round((1 - pack_cost / sale_price) * 100, 2) else 0 end
```

판매가가 0이면 마진율 0, 상태는 `normal` 이다.
즉 **판매가를 입력하지 않은 제품이 "정상 · 0.0%"** 로 초록색으로 표시된다.
값을 모르는 것과 정상인 것이 구분되지 않는다.
